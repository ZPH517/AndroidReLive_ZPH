# 开发指南

写给要改这个项目的人。读完应该能回答三个问题：

1. 画面是怎么从设备跑到浏览器上的
2. 代码为什么这样分层
3. 哪些地方看着奇怪、但绝对别改（都是坑换来的）

> 只想用工具的话看 [README](../README.md)。后面还能做什么，见文末[路线图](#附录-a-路线图)。

## 一、整体架构

```text
┌─ 浏览器 ────────────────────────────────────────────────────────────┐
│                                                                    │
│  index.html  ── importmap ──▶ js/vendor/*.js  (Tango WebUSB 实现)  │
│       │                        js/vendor/relive.bundle.js          │
│       │                                        │                   │
│       │  window.ReLive                         │                   │
│       ▼                                        ▼                   │
│  ┌─────────────┐   ┌──────────────────────────────────────┐        │
│  │ 桌面窗口系统 │   │ src/relive/  投屏会话                 │        │
│  │ desktop/    │   │  session.js  启动参数 / 视频流 / 画布 │        │
│  │ 任务栏/拖拽 │   │  device.js   设备 shell / 清理 / 取证 │        │
│  └──────┬──────┘   │  input.js    鼠标键盘 → 控制消息      │        │
│         │          └───────────────┬──────────────────────┘        │
│         │                          │                               │
│  ┌──────▼────────┐                 │  WebUSB (独占)                │
│  │ 工具面板      │─────────────────┘                               │
│  │ files/ apps/  │                                                 │
│  │ terminal/     │                                                 │
│  │ tools/        │                                                 │
│  └───────────────┘                                                 │
└────────────────────────────────┬───────────────────────────────────┘
                                 │ USB 数据线
┌────────────────────────────────▼───────────────────────────────────┐
│ 安卓设备                                                           │
│  adbd ──┬── scrcpy-server (app_process 起的 Java 服务)             │
│         │      │  H.264 编码 / 虚拟屏 / 输入注入                    │
│         │      └──▶ localabstract:scrcpy_<scid>                    │
│         └── shell / sync (文件传输) / logcat                       │
└────────────────────────────────────────────────────────────────────┘
```

**没有中转服务器**。浏览器通过 WebUSB 直接跟设备的 `adbd` 说话，
画面走 `tunnel_forward` 建立的反向通道传回浏览器，用 WebCodecs 硬解、Canvas 绘制。
所有数据只在 USB 线上跑。

## 二、画面怎么出来的（一次完整启动）

```text
1. 用户点「连接设备」
   └─ navigator.usb.requestDevice() → 拿到 USB 设备
   └─ 建 Adb 实例（Tango 的 credential 存在 IndexedDB）

2. 自动启动主屏镜像
   ├─ 核对设备上的 scrcpy-server.jar 字节数（不符就重推，见坑 #3）
   ├─ 清理设备端残留 scrcpy 进程（见坑 #2）
   ├─ clearScrcpyReverse() 撤掉可能残留的反向转发
   ├─ 唤醒屏幕（KEYCODE_WAKEUP，让熄屏的设备能出画面）
   │
   ├─ adb reverse tcp:27183 → localabstract:scrcpy_<scid>
   ├─ 启动：CLASSPATH=... app_process / com.genymobile.scrcpy.Server 3.3.3
   │         max_size=1280 max_fps=30 tunnel_forward=true scid=<scid> audio=false
   │
   ├─ 服务端建 MediaCodec（c2.unisoc.avc.encoder 之类）开始编码
   ├─ 客户端连上通道，读到 SPS/PPS → 拿到宽高
   └─ videoStream → WebCodecs VideoDecoder → frame → CanvasRenderer.draw()

3. 输入
   user pointerdown → input.js 换算成视频坐标 → controller.injectTouch(...)
   └─ 走控制通道回设备 → 系统当作真实触摸

4. 关闭
   ├─ input.dispose()
   ├─ decoder.dispose()
   ├─ client.close()          ← 只关 socket，**不杀设备端进程**
   └─ killServerByScid()      ← 所以必须补这一刀（坑 #2）
```

**关键点**：`tunnel_forward` 模式下，服务端不是监听端口等浏览器连，
而是反过来通过 `localabstract` socket 连 `adbd`。这条通道由 `scid` 区分，
不同会话各走各的。

## 三、为什么这样分层

`src/relive/` 只有三层，边界很硬：

| 文件 | 能做什么 | 绝对不能做什么 |
| --- | --- | --- |
| `device.js` | 拼 shell 命令、读设备状态、杀进程、抓 logcat | 碰 WebUSB 对象以外的任何东西、碰解码、碰画布 |
| `session.js` | 组织启动参数、管视频流、管会话生命周期 | 写具体 shell 命令字符串（那属于 device.js） |
| `input.js` | 坐标换算、事件映射 | 管会话、管连接 |

这么分的实际原因：**投屏失败时的排查路径几乎全在设备侧**。
把「往设备上跑命令」集中到一个文件，出问题只需要读一个文件，
不用在 1000 多行里找哪句命令拼错了。

历史上 `src/relive/session.js` 曾经是一个 1284 行的文件，
所有设备命令、清理逻辑、重试流程、解码渲染都混在一起，
结果就是「修一个 bug 顺手改坏两个」——所以拆开了。

## 四、启动失败的重试策略

启动不是一次成功就完事，弱设备上失败率不低。`startSession()` 的流程：

```text
第 1 次：正常启动（带 scid）
  ├─ 成功 → 返回
  └─ 失败 ↓
     ├─ 重放一次启动命令，拿到完整 stderr + 退出码（浏览器侧管道会丢输出）
     ├─ dumpCrashLog：抓 logcat crash / main / 全缓冲 + 屏幕状态 + scrcpy 进程列表
     ├─ killServerByScid(本次的 scid)   ← 只杀这次失败的那个，不动别的会话
     ├─ 重新唤醒屏幕                    ← 熄屏导致的失败，这一步常能救回来
     └─ waitForServerGone()             ← 轮询 /proc 直到真的没了，最多 6 秒

第 2 次：清除本次失败进程后重试（新 scid）
  └─ 失败 ↓

第 3 次：不带 scid，用默认 socket 名（排除 socket 隔离的兼容问题）
  └─ 失败 → 抛出，前端显示错误卡片 + 日志
```

**为什么要重放**：`client` 那条管道在进程早退时会丢输出，
第一次往往只看到一行 `Aborted`。重放是原样再跑一次那条命令，
带上 `2>&1` 和 `echo __EXIT=$?`，能拿到真正的原因。
本项目最后能定位到「jar 被系统清掉」，靠的就是重放后的 logcat 原文：

```
W System  : ClassLoader referenced unknown path: /data/local/tmp/scrcpy-server-v3.3.3.jar
E appproc  : ERROR: could not find class 'com.genymobile.scrcpy.Server'
Abort message: 'No pending exception expected: java.lang.ClassNotFoundException...'
```

只看 `Aborted` 的话，会误判成「编码器被占」或「反向转发冲突」，方向全错。

## 五、踩过的坑（改代码前必读）

这一节是这份文档存在的主要理由。每条都真实发生过，代价以「天」计。

### 坑 1：设备端 shell 脚本从来没被执行过

**现象**：加了一堆清理、诊断、唤醒命令，日志显示「已清理」「已发送」，
但设备端行为毫无变化；某些命令打印 `Usage: input ...` 或
`/system/bin/sh: syntax error: unexpected 'do'`；`echo alive` 返回空。

**根因**：投屏库把参数数组用**空格拼成一条字符串**交给设备的 shell：

```js
// @yume-chan/adb 内部
const socket = await this.#adb.createSocket(`exec:${command.join(" ")}`);
```

于是这行代码：

```js
spawnWaitText(["sh", "-c", 'PIDS=$(grep ...); kill -9 $PIDS; echo LEFT=$LEFT'])
```

拼出来是：

```
sh -c PIDS=$(grep ...); kill -9 $PIDS; echo LEFT=$LEFT
```

设备端 shell 只把 `-c` 后面**第一个词**（`PIDS=`）当脚本，其余全变成位置参数。
后果极其隐蔽，因为**它不会报错失败，只会给出假结论**：

| 我们以为在跑 | 实际发生 | 假象 |
| --- | --- | --- |
| `PIDS=...; kill -9 $PIDS` | 内层只跑 `PIDS=`，外层变量空 | 日志「清理完成」，一个没杀 |
| `... \| wc -l` | 内层跑裸 `grep`，报 usage 被吞 | 恒返回 0 →「没有残留进程」 |
| `for d in ...; do ... done` | 被拆成 `for` `d` `in`… | `syntax error: unexpected 'do'` |
| `input keyevent KEYCODE_WAKEUP` | 内层跑裸 `input` | `Usage: input ...` |
| `echo alive` | 内层跑裸 `echo` | 「连接存活：无输出」 |
| `timeout 6 xx; echo __EXIT=$?` | 退出码取的是假的内层 | 「退出码 0（正常）」 |

**修法**：新增 `shCmd(adb, script)`，整段脚本作为**一个参数**传：

```js
function shCmd(adb, script) {
  return adb.subprocess.noneProtocol.spawnWaitText([script]);
}
```

全项目 7 处 `["sh", "-c", X]` 全部替换，一处不留。

**教训**：诊断工具本身先要可靠。这一条把后面所有排查都带偏了——
因为所有诊断输出都是假的，越修越迷信自己的假设。
**先确认你的观测手段是真的，再谈定位。**

### 坑 2：`process.kill()` 杀不掉设备端的进程

**现象**：关闭镜像再打开，永远 `Aborted`，重试三次全崩。

**根因**：`@yume-chan/adb` 的 `process.kill()` 实现是 `this.#socket.close()`——
**只关浏览器这边的 ADB socket，设备上的 `app_process` 还活着**。
旧进程一直占着硬件编码器（展锐 / 部分联发科只有一路），新进程一启动抢不到编码器 → SIGABRT。

附带问题：原来清理用 `ps -A -o PID,ARGS | grep ...`，
某些 ROM 上 `ps` 参数支持不全，**静默失败、一个进程都没杀到**，还打出一句假的「已清理」。

**修法**：
- 不依赖 `ps`，直接读 `/proc/<pid>/cmdline` 找进程：

  ```sh
  grep -l "[c]om.genymobile.scrcpy.Server" /proc/[0-9]*/cmdline | cut -d/ -f3
  ```

- `[c]om` 括号技巧：模式写成 `[c]om...` 既匹配真实进程命令行里的 `com...`，
  又不会匹配到「正在执行这条扫描命令的 shell 自己」（否则 `kill -9` 会把自己也杀掉，
  清理半途而废）。按 scid 杀时同理用 `s[c]id=`。
- 先 `kill -15` 给服务端机会正常释放 MediaCodec / Surface，0.5 秒后还没走的 `kill -9`
- **杀完再数一遍**，把真实剩余数打进日志。数字是 0 才算真干净。

### 坑 3：设备上的 jar 被系统清掉了

**现象**：第一次连接正常，用一会儿关掉，再开就 `Aborted`，
而且怎么重试都没用（重试不会重新推送 jar）。

**根因**：`pushServer()` 用一个 WeakSet 记「这台设备推过了」，
**推过就永远不再推**。而 `/data/local/tmp/` 会被某些 ROM 的「加速清理」抹掉。
文件没了 → `app_process` 加载不到类 → ART 直接 abort（退出码 134）。

**修法**：每次启动前核对设备上那份 jar 的**真实字节数**：

```sh
[ -f /data/local/tmp/scrcpy-server-v3.3.3.jar ] && wc -c < 该文件 || echo MISSING
```

与浏览器里打包的那份长度比对，不符就重推；推完再核对一次，仍不符再推一次。
88 KB 的推送不到半秒，比事后猜半天便宜太多。

**教训**：不要把「一次性初始化」当成永久有效。设备是别人的，磁盘随时可能被清。

### 坑 4：`await` 漏了，导致所有判断恒为真

```js
// 错：wakeLike 是 async，没 await，拿到的是 Promise
const text = wakeLike(adb, 'input keyevent KEYCODE_WAKEUP', log);
if (INJECT_DENIED.test(text)) { ... }   // Promise 转字符串，永远不匹配
```

结果：「点亮成功」永远为真、小米的权限拦截永远判不出来。
`wakeLike` 是 async，所有调用点都必须 `await`。

### 坑 5：透明层把鼠标全吞了

早期桌面容器是覆盖整个画面的绝对定位层，鼠标事件全被它接住，
投屏画面一个点击都收不到。

**修法**：桌面层 `pointer-events: none`，**只有窗口自身**（`.win { pointer-events: auto }`）接收事件。
窗口内还要在冒泡阶段截断，拖标题栏才不会漏到画面的触摸注入上。

### 坑 6：全屏预览被任务栏压住

文件预览的 `.pv.max` 是 `position: fixed`，
但它的祖先里有 `transform`（窗口缩放用过），
于是 `fixed` 不再是相对视口，而是相对那个祖先——全屏盖不满整屏，上面压着任务栏。

**修法**：
1. 窗口一律用 `left/top` 定位，**绝不用 `transform`**
2. 全屏预览时把节点临时挂到 `body` 根部（`z-index: 10000`），关闭时挂回原位

## 六、输入链路

```text
pointerdown/move/up
  → 取相对 canvas 的坐标
  → 除以 canvas 显示尺寸、乘以视频真实尺寸   ← 缩放后必须反算
  → { action, pointerX, pointerY, pressure, actionButton, buttons }
  → controller.injectTouch(...)
```

键位映射：可打印字符走 `injectText`，功能键走 `injectKeyCode`。
鼠标右键→返回、中键→Home、侧键→最近任务。

**`[输入]` 日志**：开了「详细日志」后每条事件都会打出来，
排查「点不准」「拖不动」时看这个，比猜快得多。

## 七、桌面窗口系统的三条硬规矩

`src/desktop/index.js` 里写死的规则，违反其中任何一条都会退化成 bug：

1. **桌面层 `pointer-events: none`，窗口自身 `auto`** —— 否则吞掉投屏鼠标（坑 #5）
2. **窗口定位用 `left/top`，绝不用 `transform`** —— 否则 `position: fixed` 的后代会被困在窗口里（坑 #6）
3. **最小化只隐藏 DOM，不销毁面板** —— 终端的 shell 会话、文件的当前目录、应用列表都靠这个保住

另外：窗口一旦被拖到可视区外，自动拉回来，否则用户找不回来只能刷新页面。

## 八、其它模块的复用策略

控制台的工具面板没有另起一套命令层，而是**直接复用 `js/core/` 里已经实测过的逻辑**：

| 面板 | 复用什么 | 为什么 |
| --- | --- | --- |
| 应用管理 | `js/core/core.js` 的 `GJ.Service`：`packageAction()` / `extract()` / `install()` | `pm` 的参数顺序在不同 ROM 上差异极大（`--user 0`、系统包要带 `-k`、恢复用 `install-existing`），自己拼一套必然翻车 |
| 设备状态 | `GJ.props` / `display` / `battery` / `duration` / `deviceName` 的解析函数 | 字段名各 ROM 不同，作者已经适配过 |
| 终端 | `js/core/terminal.js` 的 `GJTerminal.Controller` | xterm 渲染、Ctrl+C、resize 都跑通了，别重造 |

**原则**：能在上游已经跑通的代码上包一层，就不要重写一遍再踩一次 ROM 差异。

## 九、调试手段

### 日志分级

`log(text, kind)` 的 `kind`：

- `""`（默认）—— 正常信息
- `"dim"` —— 诊断细节，只有开「详细日志」才显示
- `"ok"` —— 成功
- `"err"` —— 错误，红色

**新加日志时想清楚该用哪级**。默认级别刷一大堆 `[诊断]` 出来，会淹没真正有用的信息；
反过来把有用的降级成 `dim`，用户不开详细日志就永远看不到。

### 排查顺序（投屏起不来时）

1. 看 `[清理]` 那行——数字非 0 说明真的杀到了进程
2. 看 `启动异常` 后面跟的原文，通常是 `Aborted`（信息量很低）
3. 看重放结果里的**退出码**：134=SIGABRT、139=SIGSEGV、124=还活着在等 socket（命令本身没问题）
4. 看 `设备端日志·scrcpy 进程`——里还有 pid 说明没杀干净；是空的却仍失败，说明问题不在进程
5. 看 `设备端日志·crash 缓冲区`——**这是最有信息量的一条**，
   `Abort message` 会直接告诉你原因（ClassNotFound / 编码器 / 权限）
6. 看 `设备端日志·连接存活`——如果连 `echo alive` 都空，说明 ADB 通道已经不正常了

### 手动验证设备端命令

不确定某个 shell 命令在目标设备上是什么行为时，先别改代码，
在控制台的「终端」面板里手动跑一遍。命令原样能跑通，再写进 `device.js`。

## 十一、无线连接（桥接）是怎么走的

USB 模式靠 WebUSB 直连设备；**无线模式浏览器不能直接连**，因为网页既不能用 WebUSB 走 Wi-Fi，
也不能自己开 TCP 去连手机 ADB 端口。所以无线模式多了一层**本地桥接程序** `bridge.mjs`。

```
浏览器（Chrome）
   │  WebSocket（localhost，电脑内部）
   ▼
bridge.mjs（本地，:8126，仅绑 127.0.0.1）
   │  Wi-Fi / TCP(+TLS)
   ▼
手机：开发者选项 → 无线调试（mDNS 广播 + TLS 配对端口）
```

要点：

- **桥背后要有一个真正的 adb 服务端**。`@yume-chan/adb` 只提供了 ADB 服务端协议的**客户端**
  （`AdbServerClient` + `WirelessCommands` / `MDnsCommands`），不自带服务端实现。所以 `bridge.mjs`
  会按需 `adb start-server` 拉起本机 adb（默认 5037），再把浏览器的字节管道接到它上面。
  `adb` 路径会自动在常见位置探测，找不到就靠环境变量 `ADB_BIN` 指定。
- **两条连接路径复用同一套上层**：
  - 自动发现 / 配对后连接走 `transport.connectServer` → WS `/server` → 本机 adb server → `host:connect:`。
  - 手动 IP 直连走 `transport.connectTcp` → WS `/adb` → 直接连设备端口（这条不依赖本机 adb）。
- **桥只绑 127.0.0.1**，局域网其它机器连不进来；ADB 端口也不暴露到公网，安全模型和 USB 一致。
- 桥的 WebSocket 服务端是**自己实现的**（握手 + 帧编解码，约 80 行），不引入额外依赖，保持项目精简。
- 无线调试是 Android 11+ 自带功能，**不需要 root**；但它等于「同 Wi-Fi 可读写手机」，只在可信 Wi-Fi 用。

调试无线问题时，先点网页「测试」确认桥已起；再看控制台日志里有没有
`经无线桥接连接 …` / `镜像失败：…` 这类字样，按 USB 模式的同类日志去定位即可。

## 附录 A：路线图

按「价值 ÷ 成本」排的，想贡献可以直接挑一条开 issue 认领。
成本是**有 WebUSB / Android 基础的人**的估算，不是绝对工时。

### 先做这些（成本低，用户立刻能感觉到）

| # | 功能 | 成本 | 说明 |
|---|---|---|---|
| 1 | 文件拖拽上传 | 低 | 整个页面做成 drop zone，拖进去自动传到当前目录 |
| 2 | 画面缩放与平移 | 低 | 现在画面固定贴合窗口；加缩放在小屏设备上很有用 |
| 3 | 屏幕录制 | 低 | 直接录 canvas（`captureStream` + MediaRecorder），不占设备资源 |
| 4 | 画质 / 帧率滑块 | 低 | 把 `session.js` 里写死的 `maxSize/maxFps/bitRate` 暴露成 UI |
| 5 | 诊断报告一键复制 | 低 | 把版本、设备、最近日志、失败原因拼成一段文本。**决定维护累不累的头号功能** |
| 6 | PWA 化 | 低 | 加 manifest + service worker，装成桌面应用 |
| 7 | 常用操作快捷键 | 低 | Ctrl+V 粘贴、Esc 返回、Alt+Home 之类 |

### 值得投入（真正的能力扩展）

| # | 功能 | 成本 | 说明 |
|---|---|---|---|
| 8 | **无线连接（ADB over Wi-Fi）** | 中 | **价值最高的一条**。现在必须插线，而"复活旧设备"的真实用法是让它长期挂着当副屏。浏览器开不了 TCP，需要配一个几十行的本地转发助手 |
| 9 | 音频转发 | 中 | scrcpy 3.x 支持 `audio=true`，浏览器侧要接 AudioWorklet 或 WebCodecs 解码 |
| 10 | 应用图标墙 | 中 | 已能解析 APK 名称与图标，做成网格当"新桌面" |
| 11 | 剪贴板双向同步 | 中 | 电脑 ⌘C → 设备，设备复制 → 电脑 |
| 12 | 操作录制与回放 | 中 | 记录触摸序列，可重放（批量调试旧设备时有用） |
| 13 | 多设备并行 | 中高 | 同时连两台，各开一个控制台窗口。难点是 WebUSB 接口独占的管理 |

### 长期方向（需要新架构或外部条件）

| # | 功能 | 成本 | 说明 |
|---|---|---|---|
| 14 | 虚拟屏多窗口 | 中 | 代码思路在 git 历史里能找到。**只有单编码器设备的用户别指望它**，这是硬件限制 |
| 15 | 设备端守护与自动重连 | 中 | 插拔、休眠后自动恢复会话 |
| 16 | WebRTC 远程共享 | 高 | 把画面推给远端，脱离"同一根 USB 线"的限制。涉及信令与安全设计 |

## 附录 B：贡献

### 环境

```bash
npm install      # 只有改 src/ 才需要
npm start        # 127.0.0.1:8125
npm run build    # 改完 src/ 必须重建产物
npm run check    # 确认关键符号都进了产物、页面里每个引用都指向真实文件
```

### 提交前请自查

1. `npm run build` 跑过了吗？**改了 `src/` 却没重建 bundle，是最常见的 PR 问题**——
   别人拉下来运行的是旧代码，现象对不上，排查成本很高。
2. `npm run check` 过了吗？
3. 真机验证过了吗？如果没设备，请在 PR 里说清楚"未实机验证"，别让人误以为测过。
4. 新加的日志分级对不对？见[日志分级](#日志分级)——默认级别别刷诊断信息。
5. 碰了 `device.js` 里的 shell 命令？先在真机终端里跑一遍原样命令。

### 代码风格

- 不引新依赖（除非必要，且要说明理由）。现在整个前端只依赖 Tango / ya-webadb、xterm.js、scrcpy-server 三样。
- 注释写**为什么**，不写**做了什么**。上面那些坑全是"看起来多余其实不能删"的代码，务必留注释。
- 中文注释、中文日志，保持现有风格。

### 设备兼容性反馈

欢迎按以下格式提 issue，帮助补充[兼容性矩阵](#十兼容性矩阵实测)：

```
设备型号 / 平台（高通/联发科/展锐/麒麟）
Android 版本
结果：投屏正常 / 能看不能点 / 启动失败
失败的话：控制台日志里 [清理]、scrcpy-server、crash 缓冲区那几行
```

Pages 是 HTTPS，**WebUSB 能直接用**，挂上去就是在线体验链接——
这是这类纯前端工具最大的优势，别人点开就能试，不用先 clone。
